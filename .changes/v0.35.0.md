## v0.35.0 - 2026-11-16
### Added
* Gitea and Forgejo runners run the tasks they fetch and report them (#520, G4): the task's job goes through the same steps, memory gate, trust decision and step cache as a GitHub job, and its steps, logs, outputs and result reach the instance as it runs, with the instance's cancel and the job's timeout-minutes (default 360) stopping it through the usual cancel ladder. Checkout fetches from the instance with the task's own token. No run state is written to the database for these platforms.
* A step-end: line for every step (its time and, for native steps, its cgroup's CPU, peak memory, I/O and page faults, and its sandbox's set-up phases) and a request: line for every HTTP request to GitHub, Gitea or Forgejo (DNS, connect, TLS and first-byte times, rate limit headers, retries), for finding where a job's time and resources go. RUNNER_LOG_REQUESTS=0 turns the request lines off. See docs/OPERATIONS.md.
* docs/BENCHMARKS.md: a study of the runner's compute-bound stages against C and Rust implementations (zstd and gzip inflating, SHA-256, secret masking, tar, parsing), with what was adopted, what was rejected and the one measurement the Xeon is needed for
* Native jobs of a Gitea or Forgejo runner reach the instance they came from, so actions/checkout works: the instance's address and port (and the one its tasks name) are opened to the job's network, and nothing else of the host's. An instance on the host's loopback is served at the bridge's address by a forwarder in the runner (docs/native-backend.md).
* The runner links musl libc and a Rust static library (runner/rust/zr-net, a tokio runtime behind a small C ABI) as the first step of moving HTTP, the live feed and the database TLS to hyper and rustls (docs/rust-net.md has the design); the binary grows by 0.6 MB (x86_64) and 0.5 MB (aarch64), tests now build for musl, and cargo-deny checks the crates
* The database connection's TLS is rustls (the network library) instead of tls.zig, which is gone: it takes a client certificate and a private CA (sslcert, sslkey, sslrootcert in the URL or PGSSLCERT, PGSSLKEY, PGSSLROOTCERT), reads the system roots from SSL_CERT_FILE or SSL_CERT_DIR, and checks certificates more strictly (a CA certificate used as the server's, or a name only in the subject, is refused: see deploy/runner.env.example)
* The runner's GitHub App, OAuth and registration calls (auth, app, jitconfig) go through the network library's HTTP client (rustls over hyper) instead of std's, which sets TCP_NODELAY, drops credentials on a redirect to another origin, reads HTTPS_PROXY, HTTP_PROXY and NO_PROXY and SSL_CERT_FILE, and logs one request: line per call with exact DNS, connect, TLS and first-byte times
* A step compares the database's old TLS client (tls.zig, now a lazy dependency only the step fetches) with the rustls one on the same servers: `zig build test-tls-oracle -Dtls-oracle`, run by a job of its own, "TLS oracle"; the differences left (a CA certificate as the server's own, a name only in the subject, client certificates) are written down in docs/rust-net.md
* Downloads, the log upload and the image registry go through the Rust network library with streaming bodies (R4 of docs/rust-net.md): a Zig release tarball is hashed as it arrives instead of held (about 50 MB less memory at startup), a layer or a log of any size costs the library's 1 MiB queue, kept connections are reused per host, and `request:` lines are written for them with the library's exact figures; the registry's hand-written redirect workaround and stale-connection retries are gone (the library drops `Authorization` on a redirect to another origin and replaces a closed kept connection itself)
* Native jobs in an image with no git (slim and Alpine images) fetch the checkout and `uses:` actions from the repository's tarball, as actions/checkout does, instead of going to the Dagger engine or failing
* With RUNNER_ENGINE=none, a local `uses: ./path` action that is not in the job's commit (made by an earlier step, or in another repository's checkout) is read from the workspace when its step runs, instead of the job being refused before any step
* A native job whose container `options:` carry `--cpus` (or `--cpu-quota` and `--cpu-period`) no longer falls back to the Dagger engine: the runner sets `cpu.max` on the job's cgroup as Docker does (`--cpus 0.5` is 50000 of every 100000 µs), asking its parent for the cpu controller when it does not give it. Values are read as Docker reads them (decimals such as 0.5 and 1.5, `a/b`; negative, too precise, a quota under 1 ms, a period outside 1 ms to 1 s, and `--cpus` with a quota or period are refused with the flag named). Where the cpu controller cannot be delegated or the job has no cgroup, the native set-up fails saying so (the job then goes to Dagger, which drops the flag) instead of running unlimited.
* The run service, the broker (its long poll, the Dagger engine's queries) and the Gitea and Forgejo client go through the network library (`broker.request` on `net_client`): one pool, one CA load, one `request:` line implementation, redirects and the stale-connection retry in the library; the runner's std HTTP client now serves only the live feed (moved in R6). Differences: a redirect of a request with a body is followed (a 302 of a POST becomes a GET; a streamed body refuses a redirect) where std handed the 3xx back, the User-Agent is zig-runner/<version>, errors carry the library's names (DnsFailed, NetworkIo, TooManyRedirects), no Accept-Encoding is sent, and the request: line shows the port of an explicit one in every call
* Container `options:` `--cpu-shares` (as `cpu.weight`), `--cpuset-cpus` and `--cpuset-mems` (as `cpuset.cpus` and `cpuset.mems`, checked against what the machine allows), `--pids-limit` (lowers `pids.max`, never raises it) and `--memory-swap` (as the job's own `memory.swap.max`, see the Changed entry) no longer send a native job to Dagger. Deliberate differences from Docker: `--cpus` above the machine's CPU count is accepted and never throttles, a negative `--cpu-quota` is no quota, and `--cpu-shares` becomes a weight as systemd converts it (1024 shares is the default weight 100; runc's formula gives 39) so a job that asks for the default competes as an equal.
* The native Dockerfile builder builds multi-stage Dockerfiles (stages keyed one on another, `COPY --from` a stage or an image, only the stages the last needs), wildcards in `COPY` and `ADD`, `.dockerignore`, `ADD` of a URL, heredocs, `SHELL`, `FROM scratch`, `FROM --platform` and `COPY --chown` by name, and a Dockerfile action of the job's own repository from the job's files, so these no longer send a job to the Dagger engine; `dockerfile-diff.sh` compares its images with BuildKit's weekly, and a fuzz target covers its parser (differences in docs/native-backend.md)
* A memory soak for the runner (`.github/scripts/memory-soak.sh`): 500 jobs of seven shapes (run steps, checkout, a container, a failing job, a cancelled job, a large log, a step timeout) through one native runner in a capped container against a local Gitea, sampling after each job and failing when resident or anonymous memory, the heap, the network library's counter, descriptors, threads, mounts or zombies grow past their margins. The nightly analysis run does a 50-job version.
* Job priority, a feature GitHub Actions does not have (prototype). A job gets a level from a policy file (`RUNNER_PRIORITY_POLICY`: `high repo=o/r event=push ref=refs/heads/main`), its own `ZIG_RUNNER_PRIORITY` env (capped, and at the default level for jobs the runner does not vouch for), or the pool default. Jobs waiting for room at the memory gate start by level, a job rising one level for each `RUNNER_PRIORITY_AGE_SECS` it waits so none starves (the bound is `(9 - level)` steps), with the #415 backfill unchanged. Native jobs get `cpu.weight`, `io.weight` and (high) `memory.low` by level, and with `RUNNER_PRIORITY_FREEZE` the steps of lower jobs are frozen under memory pressure while a higher one runs, never longer than `RUNNER_PRIORITY_FREEZE_MAX_SECS`. Nothing changes while every job has the default level.
* Deploy channels (#550): every push to main and every tag vX.Y.Z-rcN is built, attested and published as a GitHub pre-release (the `candidate` workflow: main-N-SHA12, with binaries saying vX.Y.Z-main.N+SHA12; never latest), and zig-runner-deploy follows a channel per agent (`CHANNEL=stable|rc|main`, `zig-runner-deploy@.service` for a second pool beside the stable one) with the same checksum and provenance checks against the right workflow, ref and commit, a version monotonic within the channel, and an explicit, logged switch between channels. `stable`, the default, installs releases only and refuses a candidate (tested against hostile feeds and deployment orders). Candidates are pruned past a retention window (14 days, `CANDIDATE_RETENTION_DAYS`; the newest `CANDIDATE_KEEP`=20 of each kind and what the rc pool is deployed from stay; `candidate-prune` daily, with a dry run). A release candidate also gets an image (`:vX.Y.Z-rcN`, and `:rc` while it is the newest; never `:latest`) and a deployment record to `razorbill-rc`; a main candidate has neither. docs/OPERATIONS.md has a "Channels" section
* The pre-push hook names the log of its long steps as they start (`build and tests (output: /tmp/pre-push-tests.…)`), so `tail -f` follows them, and `PRE_PUSH_VERBOSE=1 git push` shows every check's output as it runs; by default each step still prints only its name and a summary line.
* CI's Test step prints the memory peak of the compile and of the run apart, one `memory-peak: phase=... peak_mb=... source=cgroup|cgroup-total|time|none` line each (from the step's cgroup, or the largest process where there is none), to measure the Pi's compile spike that came within a few percent of the job's 3.1 GB limit; new `zig build test-compile` step.
* Each native step's log ends with its memory peak ("Native steps: this step's memory peak was 2410 MB of the job's 4.5 GB limit"), also when the step was OOM-killed, and the journal has a matching kind=step_memory_peak line (step, peak_mb, limit_mb, scope=step|job), so CI sees how close a step came to its limit without help from the job's image. On kernels before 6.12 the peak cannot be reset per step and the line says "peak so far" (scope=job); with no memory.peak (cgroup v1, Linux before 5.19) there is no line. See docs/native-backend.md.
* Native jobs and the runner's own requests log slow or failed name lookups: warn kind=dns_lookup_slow (over 2 s) and kind=dns_lookup_failed, with the name, the time and the nameserver, so a DNS stall (#522) can be shown from the journal. Nothing about a job's resolver changes.
* OpenSSF Scorecard's Fuzzing check finds libFuzzer targets for the network library (runner/rust/zr-net/fuzz): what an HTTP server answers the client with (redirects, headers, body limits, chunked and streamed bodies), what a caller's request becomes on the wire, and what a TLS server sends, through the C ABI Zig calls and under AddressSanitizer. A pull request that changes the library builds them; the night fuzzes each for a minute (analysis.yml, zr-net-fuzz).
### Changed
* zstd layers are decompressed with libzstd (vendored, decompressor only, built into the static binaries for x86_64 and arm64) instead of the runner's own decoder: 3.7 times the speed and half the CPU for a pull. The own decoder stays as the oracle libzstd is fuzzed and tested against
* Masking secrets in a step's log is 5 to 6 times faster: a position of a line is tested against the first two bytes any mask can start with before the trie is walked (the result is the same)
* A job's layers are canonicalised faster: the step's ids are shifted with one xattr listing per entry instead of three reads through the descriptor's magic link, so an upper of 3,000 files takes about 40 ms instead of 72 ms. The same ids, set-id bits, capabilities and ACLs result.
* gzip layers are inflated with zlib-ng (vendored, inflater only, built into the static binaries for x86_64 and arm64) instead of Zig's std: 3 times the speed, and 40% less CPU for a pull. std's inflater stays as the oracle zlib-ng is fuzzed and tested against. A gzip layer with a reserved header flag or a wrong trailer is now refused, where std let it through
* The runner's HTTP connections to GitHub, Gitea and Forgejo set TCP_NODELAY: a new TLS connection no longer waits about 40 ms for Nagle's algorithm and the peer's delayed ACK (45 ms against 2.2 ms for a cold request, measured locally).
* Renovate proposes new libzstd releases (vendor-zstd.sh's version); the tarball's SHA-256 and the vendored files then follow by hand, which CI's vendored-libzstd check enforces by failing, with the new hash in its message
* Renovate proposes new zlib-ng tags (vendor-zlib-ng.sh's tag); the commit it names and the vendored files then follow by hand, which CI's vendored-zlib-ng check enforces by failing, with the commit to pin in its message
* CI builds the release binaries once for the merge queue's ci run: the arm64 check runs the x86_64 job's build instead of compiling it again
* The runner's own warnings and errors have one format, `warn: kind=… key=value` or `error: kind=… key=value` (documented in docs/OPERATIONS.md), so that a grep or an alert can key on them; plain log lines get `kind=<prefix> msg="…"`. Lines that changed: the log upload failures, `error during …`, `github error: …`, `trying again`, `could not remove runner registration`, the memory gate's and the Gitea poller's warnings. While no job runs, a `health: proc` line is logged every 15 minutes (`RUNNER_HEALTH_IDLE_INTERVAL`, 0 for none), so growth between jobs shows.
* The broker, run service, results service and Gitea client no longer send a POST again after a timeout or a lost connection unless it is one the server answers the same when it comes twice: each call now says (`broker.Resend`). GETs, DELETEs, the run service's acquirejob, renewjob and completejob (actions/runner retries them too) and Gitea's Declare and UpdateLog are sent once more on a new connection; session creation, acknowledge, the results metadata and step updates, Gitea's Register, FetchTask and UpdateTask, and the Dagger engine's queries are not. A closed kept connection is still replaced unseen
* A native job container's `--memory-swap` now sets the job's own `memory.swap.max` as Docker reads it (0 by default and when equal to `--memory`; the difference when larger; `max` for -1), up to what `RUNNER_NATIVE_SWAP` allows: where jobs may not swap it is capped to 0 and "Set up job" says so. A `--cpus` or `--cpu-quota` above the kernel's maximum, and a `--cpuset-cpus` list past 8192 ids on big machines, are now handled (refused with the flag named, and accepted).
* The health line's heap= and rust= sizes are exact KiB (heap=510K/9), not rounded to MiB from 10 MiB up, so the memory soak resolves them
* No swap unless asked: every native job with a cgroup now has its own `memory.swap.max` at 0, container options or not, and only its `--memory-swap` raises it. `RUNNER_NATIVE_SWAP=true` now means jobs may ask for swap (false still caps every job to 0). `memory.high` is set only for a job that has swap (on a machine that has some): a job that asks for swap with `--memory-swap` gets the gate's, and a job with swap 0 gets none.
* Pull requests reach `main` by rebase, so its history stays linear: auto-merge asks for a rebase merge, and CONTRIBUTING.md says to rebase a branch onto `main` (never merge `main` into it).
* Native container jobs no longer ask the registry for their image on every job: a tag resolved within RUNNER_IMAGE_TAG_TTL seconds (default 300; 0 asks every time) is taken from the store, ten repeat jobs on one image cost 0 registry requests instead of 20; a registry that answers 429 or cannot be reached runs the tag's last known digest and says so in "Set up job", and with nothing known a 429 is waited out as its Retry-After asks (#551)
### Fixed
* Runners of one host keep each other's instance reach rules (each process records its instances under /run/zig-runner/reach, and every nft apply merges the live ones), the Gitea loopback forwarder binds when the pool starts, and the Zig seed registry is freed at exit.
* ThreadSanitizer builds link the network library instrumented (a pinned nightly Rust with -Zsanitizer=thread and -Zbuild-std) instead of suppressing every report with a Rust frame, so a race in or across Rust is reported; the sharded test runner now fails a test that printed a ThreadSanitizer report, and a shard that ends with a failing status, which it ignored before (it found a race in a test fake, fixed)
* The network library's HTTP client writes its request: lines through the same code and the same RUNNER_LOG_REQUESTS switch as the other requests (it had a copy of that code, and a switch main did not set)
* CI: cargo keeps its registry in the job's temp directory, so a self-hosted runner whose home .cargo belongs to another user no longer fails the build
* Native eviction tests no longer fail under load: the pass's time budget can be held still in tests, so a slow disk cannot cut a pass short (#548)
* Retries wait at least GitHub's Retry-After (seconds or a date) or the rate limit's reset on a 429, 503 or secondary-limit 403, within the caller's own budget; a push to main fails when fewer than 900 tests pass; ci.yml's comment says End to end is a required check
* Running out of memory is no longer read as an answer: allocation-failure tests of the OCI decoders, registry client, native store, Dockerfile, problem-matcher and Gitea-state code found and fixed a lock loop that spun at 100% CPU, a stale image tree built over, layers evicted and locks removed for want of memory, a Dockerfile JSON instruction read as shell text, and OutOfMemory reported as WriteFailed, Unauthorized or BadState; the Rust network library's abort on a null malloc is now documented.
* The test runner checks what the tests leave in .zig-cache/tmp, fails the run naming the tests, and removes a killed run's leftovers (chains of directories too deep to name included) at the next one; CI and the pre-push hook check the directory too (#548)
* The apt mirror fallback test serves its own signed mirror, so it no longer fails when public mirrors time out
* A kept connection the server closed under a request (hyper reports the request as canceled, nothing sent) is replaced and the request sent again, as for the other closed-connection errors; it failed with NetworkIo about one registry pull in twenty against a server that closes after every answer
* Three tests that failed on a busy machine, the HTTP hooks' lookup and connect timing, openIn under a rename storm and the results upload's retry budget, no longer depend on how long anything takes
* Job priority: a cancel, timeout or shutdown thaws a job's frozen steps before it signals them (they waited up to RUNNER_PRIORITY_FREEZE_MAX_SECS), a failed thaw is retried at the next tick, a job's directory left frozen by a dead runner is thawed when it is made again, a job holding a file lock another process waits for is not paused, and a job's own --cpu-shares wins over its level's cpu.weight. Priorities not applied (no cpu controller, no memory.low) are logged.
* The network library's TLS phase timing test no longer fails on a loaded machine: its test server now starts the 150 ms handshake delay when the ClientHello arrives, not when the connection is accepted, so a client stalled between the connect and the handshake still measures the delay (main's push CI failed with a 4.5 ms TLS phase).
* A job no longer fails with EAGAIN when other jobs on the machine are publishing layers or mounting while it opens a path through `..`: the retry gives up the CPU, then waits a millisecond between tries, for up to about a quarter of a second.
* CI's Store crash job fetches the pinned xfstests commit from kernel.org, then kernel.googlesource.com, then GitHub's mirror, giving up on one after 60 s (a dead host, or a transfer stalled for 30 s) and checking the commit's hash, so one unreachable host no longer fails the job.
* The allocation-failure test for a tree's size no longer fails when a file's blocks were being written back as it measured them (a file still being written back can show fewer blocks than it takes), as it did in CI with "expected 12288, found 16384"
* Eviction's test of a big volume counted over several passes no longer fails now and then on a loaded disk: it flushes the files it writes before the walk that sets the count to reach, since a dirty file's blocks are counted differently as the disk allocates them; two tests' pass counts became deadlines
* spin.sh leaves nothing running when it ends, on any path: an EXIT trap (also on INT and TERM) ends its heartbeat and every worker with the spin, gcc and pan it runs, and for a SIGKILL the heartbeat does so at its next tick, so a pre-push hook that ended no longer leaves a heartbeat or workers writing into a shared SPIN_DIR; two runs in one SPIN_DIR take turns (flock)
* A cancel arriving while a step's sandbox is still starting is delivered to the step, not lost: a Docker action's SIGINT is held until its PID 1 has exec'd the action's program (a post step signalled within a tick of its start lost it under load, which failed the ThreadSanitizer native job's post-script test).
* The Dockerfile builder's BuildKit oracle pins its fixtures' base images by digest (alpine:3.22@sha256:...), the form the builder has to read in FROM, an ARG's default and COPY --from (a test covers it), and Renovate keeps those digests and bases.txt together in one pull request; bases.txt names the busybox the copy-from-image fixture really uses (1.38), which the oracle missed since #busybox's bump.
* A release candidate's image scan skips the Dockerfile oracle's test fixtures, as the release's scan already did, so v*-rc* builds publish their image.
* The daily release no longer skips a release when a release candidate (vX.Y.Z-rcN) is tagged on main's head: next-version.sh now bumps from the last release tag, not the newest candidate, which sorted above it and made main read as "nothing merged since".
