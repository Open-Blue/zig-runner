## v0.38.0 - 2026-11-21
### Added
* Gitea and Forgejo steps get the variables their own runners set (#520, G5): GITEA_ACTIONS, GITEA_ACTIONS_RUNNER_VERSION and GITEA_RUN_ID on Gitea, FORGEJO_ACTIONS, FORGEJO_ACTIONS_RUNNER_VERSION and a FORGEJO_ twin of each GITHUB_ variable Forgejo's runner copies on Forgejo, and GITHUB_SERVER_URL and github.server_url have no trailing slash, as act_runner has them. The job's token is still not put in the environment (docs/GITEA.md has the table against act_runner and forgejo-runner).
* Gitea and Forgejo services: a service's own cmd: (Gitea's field) starts the image's entrypoint with those arguments on the native backend, instead of being dropped, and a Gitea task's services are tested end to end on the native backend (by name, on localhost, health check, teardown) (#520, G6). The Dagger backend logs that it ignores cmd. See docs/GITEA.md.
* docs/GITEA.md: how to serve a Gitea or Forgejo instance (install, registration, labels, trust, where a step's actions come from, the variables and services a job sees), with a pointer in the README (#520, G7). The table of where actions come from moved there from docs/OPERATIONS.md.
* CI: a job against a real Gitea and a real Forgejo ("Live gitea", "Live forgejo", .github/scripts/forge-live.sh): the runner built from the pull request serves a throwaway instance of each and four dispatched workflows check actions named by self:, a URL, $/ and the default actions URL, the variables the instance's runner sets, services and the checkout, outputs, masking and a failing step (#520, G7). Not required; see docs/CI.md.
* Gitea and Forgejo artifacts go through the instance (#520, G5): action steps get ACTIONS_RUNTIME_URL, ACTIONS_RESULTS_URL and ACTIONS_RUNTIME_TOKEN (the task's runtime token, from forgejo_runtime_token, else gitea_runtime_token, masked in the log; the job's own token when an older instance sends none, as act_runner does, and the log says which) as act_runner sets them, so artifact actions that take a Gitea or Forgejo server (forgejo/upload-artifact@v4 and download-artifact@v4) upload to and download from the instance. actions/cache stays a no-op there, as documented (docs/GITEA.md, which also says what the runtime token can do on the instance); the live Gitea and Forgejo CI jobs upload and download an artifact.
* CI tests test-files.sh's failure path with no compile: a fixture tree and a list of test names, where a file whose tests are missing from the test binary, or fewer there, must fail naming that file
* CI fails a pull request that adds a change entry of a kind that bumps the major version (Changed or Removed, as .changie.yaml's auto: major says) unless it is labelled breaking. #610 merged a fix filed as Changed, and the next release would have been v1.0.0. Only the entries a pull request adds or changes count.
* Native jobs of a runner process that end together make their last layers durable with one shared syncfs instead of one each (seven jobs ending in a burst synced the Pi's SD card seven times, 5-8 s each beside a writer): the first waits up to RUNNER_NATIVE_SETTLE_WINDOW_MS (off by default until it is measured on razorbill, #521; 100 is the window being measured) for the other jobs whose ends have begun, none when it ends alone, and jobs that end while its syncfs runs share the next. The sync goes through a descriptor the process opens before any job's, so a write error is still reported to every job it may concern; a failure refuses every layer of the batch, as a job's own failed sync does. The settle stays in the teardown, out of the job's reported time; the SPIN model of the deferred sync has the batch, and a mutant that marks a layer durable before its batch's sync fails it.
* The live log feed runs on the network library (tokio-tungstenite on the same connection, proxy and CA policy as every request, with a request: line for the upgrade); ping, pong and the close handshake are handled there and sending is bounded with backpressure. A message is now accepted when it is queued, not when it is in the kernel's buffer: a lost connection loses the queue (at most 64 KiB), the message being written, the library's write buffer (at most 64 KiB) and the kernel's buffer, and the live log feed lost line says how many queued messages were never sent; the job's log is uploaded whole either way. The upgrade request now sends User-Agent zig-runner/<version>. Rust lints (clippy, no unwrap, expect or panicking index) are enforced in CI. The std client version of the feed stays as a test oracle until its removal
### Fixed
* Gitea and Forgejo jobs fetch an action named owner/repo@ref from the instance's default actions URL (the task's gitea_default_actions_url: github.com on Gitea, data.forgejo.org on Forgejo) instead of the instance itself, and read Gitea's other forms as its model does (#520, G5): self:owner/repo[/path]@ref is the instance, https://host/owner/repo[/path]@ref is that host, and $/path is an action of the workflow's own repository at the job's commit, fetched with the task's token. ssh:// and credentials in a URL are refused with a reason. On GitHub an action's mount path (github.action_path) is unchanged, but an action whose ref has a character outside letters, digits and -_./+@, or a .. or an empty segment, is now refused with a reason before anything is fetched, as on Gitea.
* Gitea and Forgejo jobs fetch self: and $/ actions with the task's GITHUB_TOKEN, not the runtime token (which git refuses: "could not read Username"), and an action fetch no longer trips on the half-made checkout an earlier fetch of the same repository and ref left ("remote origin already exists"); two actions of one repository at one ref (the root and a directory of it) share one fetch (#520, G5).
* Gitea and Forgejo actions: an action's owner, name and ref are checked before anything is fetched (no .., no leading -, only the characters a repository name and a git ref have), so a uses: such as o/r@../../.. cannot reach a directory above the action's own or put an option on git's command line, and git's refs follow --; two servers' o/r@v1 are two trees in two directories; an instance's archive of a private repository takes the task's token when the image has no git; and the task's runtime token is never sent to git (#520, G5).
* A Gitea service's cmd: that does not evaluate fails the service with the reason in the log, instead of starting it with an empty argument (#520, G6).
* Gitea and Forgejo action trees: an action from a server other than the job's default one is mounted under a directory named by the server's whole URL (http and https of one host are two trees), and its ref's slash no longer nests one tree's directory in another's (o/r@a/b and o/r@a are two directories, whichever is fetched first). The default server keeps GitHub's path, github.action_path unchanged, where o/r@a/b is a directory inside o/r@a's as before; a fetch never deletes a directory, so both trees are there whichever is fetched first; the Dagger path mounts the same way, so two servers' o/r@v1 no longer share one mount and run the first one's code; directory names made from a ref or a host are escaped injectively (h:80 and h_80 differ), and the host of an absolute URL in uses: must be a host name or IPv4 address and an optional port (#520, G5).
* Action and checkout fetches retry a network failure: a `uses:` action's fetch and the checkout step's git (clone, tags, submodules), tarball download or Dagger fetch that fails on a DNS lookup, a refused or reset connection, a TLS failure or timeout, or a 5xx/429 is tried again, up to 5 attempts 4, 8, 16 and 32 s apart (each wait a random half to all of that), within a 180 s budget per job; a stalled transfer ends after 30 s, and no attempt that is still moving bytes is stopped before 15 minutes. Each retry is a redacted warning in the job log as it happens; the failed attempt's partial tree is dropped, and only a layer that attempt made. A missing repository or ref and refused credentials still fail at once, and a job's cancel or timeout ends the waiting. actions/runner tries 3 times, 10 to 30 s apart.
* The nightly's full test run and Valgrind job pass again: the allocation-failure sampling test and the leak test no longer depend on the environment's sampling mode, and the eviction FIFO test keeps its buffer off the stack (Valgrind reported Zig's stack probe)
* Gitea and Forgejo jobs whose image has no git no longer download an action named by an arbitrary host (uses: https://host/owner/repo@ref) from the runner's own network, which let a workflow probe the host's loopback and LAN; such an action fails its step saying that it needs git in the image, and only the instance's own server and its default actions URL are fetched by the runner (#520, G5).
* The runner's own git fetches (the native checkout and action fetches) run with git's automatic maintenance and gc off: git 2.48 and later start maintenance in the background after a fetch, which took .git/objects/maintenance.lock under the checkout's timestamp pass (touch: setting times of './.git/objects/maintenance.lock': No such file or directory) and could write a fetched layer after its step ended. A job's own git keeps its defaults.
* CI caches the Rust toolchain and the network library's build outputs between runs, keyed on the exact inputs, so an unchanged Rust side is not built again in the Database tests, TLS oracle and Tests jobs
* Install Zig no longer fails when jobs that share a tool cache install the same Zig at once, as on a self-hosted pool after a Zig version bump. Each job downloaded to one shared .part name, so the first job's rename took the file from under the second ("mv: cannot stat ....tar.xz.part"), and the second's curl rewrote the tarball the first was checking. Each job now downloads to a file of its own, checks it, and only then renames it into place. A tree in place is no longer removed before a job's own is moved in: a whole one is another job's and is used, and a bad one is renamed aside first. Found by the v0.37.0 smoke test with an empty tool cache.
* CI: the native tests as root and End to end restore the Rust toolchain and zr-net's build outputs from the cache, and the root tests are shared between their two parts by measured time.
* memory-peak.sh, which wraps CI's compile and test steps, passes an interrupt on to its command again. Bash starts a background command with SIGINT ignored, so the INT that GitHub sends first when a job is cancelled did nothing, and the step ran on until its command ended or the TERM came. The command now starts with the default action for INT and QUIT. Its self-test also checks that a signal ends the script promptly: the INT case had passed by waiting out a 30 s sleep, which cost every Workflows run 30 s.
* CI's Workflows job keeps Go's build and module caches between runs, so staticcheck, actionlint and the comparison tools are no longer compiled from source, nor the Go toolchain go-lint.sh asks for downloaded, on every run. Both caches are Go's own content-addressed stores, so an older entry is safe to restore by its prefix.
* security.yml's cargo-deny check no longer waits for rustup to install the pinned Rust toolchain and its two musl targets: cargo-deny only reads the dependency graph through cargo metadata, which any cargo answers the same way for the lock file, so it runs under the runner's default toolchain, named in the log.
* CI: on a push to main a hosted job per consumer (Tests (x86_64), Native tests as root on both architectures, End to end) builds the Rust side and saves it under the consumer's own Rust build cache key, so a merge group and a pull request's first run no longer build zr-net cold there
* CI's Rust and Go caches are saved only by pushes to main; pull requests and merge groups restore main's entries and save none. Each pull request that changed the Rust inputs or ci.yml had saved its own copies (about 1.6 GB of Rust, 0.7 GB of Go), readable by that pull request only. They filled the repository's 10 GB cache and evicted main's entries, which every merge group and pull request needs. The Rust cache warmer now fills main's entries for the jobs that don't run on a push.
* CI's TLS oracle job keeps Zig's global cache between runs, so zig build no longer compiles build.zig and Zig's build system from scratch each time: 70 s of a 230 s job on a hosted runner, about 1 s on a hit (measured in #638). The key holds the CPU model (the build runner is built for the machine's CPU), Zig's version, build.zig and build.zig.zon; only a push to main saves.
* CI: one script, allow-userns.sh, replaces the bare writes of the AppArmor user-namespace sysctl; it logs the kernel, whether the key exists and its value before and after, and a kernel without it no longer fails every native job
* Quiet CI checks fail loudly: check-names fails in CI when gh or the rulesets are unreadable, the arm64 page size is asserted, vm.mmap_rnd_bits is read back for the TSan jobs, and a failed pinned apt install (stress-ng, kcov, spin) prints what the archive offers
* #610's changelog entry is filed as a fix, as it is one, not a breaking change: it had been filed as Changed, which bumps the major version.
* Native container jobs ask the registry about a tag past its TTL with a HEAD, which Docker Hub does not count toward its pull limit, and run the stored image when the digest is unchanged, so a cached image costs one uncounted request per RUNNER_IMAGE_TAG_TTL (300 s) instead of two counted GETs; a registry that cannot answer (429, 5xx, network) runs the tag's last known digest with a warn kind=image_tag_reused line, and digest-pinned images never contact the registry once cached (#551)
* CI's Rust build cache no longer misses when GitHub rolls out a new runner image: every C compile, link and archive of the Rust builds, the host's build scripts and proc-macros included, now goes through the pinned Zig (host side for glibc 2.28) and `zig ar`, so the cached outputs do not depend on the image's compiler, linker or glibc, and the keys no longer hold the image. The shipped musl archive is byte-identical.
* The ThreadSanitizer end-to-end job no longer fails on its own diagnostics: when the runner didn't stop, e2e.sh's stuck-runner report read $backend, which isn't set in a separate e2e.sh stop call, and under set -u that failed the step after every check had passed (nightly 2026-11-20). start now records the backend for stop to read.
* A native container job's fallback to a tag's last known digest, when the registry cannot answer, ends RUNNER_IMAGE_TAG_MAX_STALE seconds (default 86400) after the registry last confirmed the tag, so a deleted or replaced tag is not run for ever; the image_tag_reused warning now has age_s and moved=true new_digest=... when a HEAD saw the tag move, and a HEAD-confirmed tag is said so in Set up job (#551)
* The image tag fallback's maximum age (RUNNER_IMAGE_TAG_MAX_STALE) is read and set atomically: every native job's start stored it into a plain global, and jobs starting at once raced on it (ThreadSanitizer, arm64 native tests).
* The runners' shared live-feed HTTPS client loads its CA bundle once at the start, on the main thread, and a renewed client does too before it is shared. Zig 0.17's std.http.Client set its TLS clock on the first HTTPS request under a lock that the TLS handshake didn't take when reading it, so runners whose first feed connects ran at once raced on it (ThreadSanitizer, the e2e suite).
* When the e2e suite gives up waiting for a run, it now says what it last saw: the attempt and status GitHub reported, how many polls failed and the last API error, and whether the suite's limit or the per-run timeout ended it. A failed wait had printed only "not done within 240 s", even once when GitHub had marked that attempt completed four minutes earlier.
* Action and repository tarballs (an image with no git) are downloaded through the network library, as every other download is, which removes the last download that used Zig's std HTTP client. The token still goes to the first origin only, and the retries of a busy server and a lost connection are kept. Against before: only 301, 302, 303, 307 and 308 are followed (it was any 3xx with a Location); a redirect from https to http is refused (it was followed with the token dropped); a connection cut in the middle of the archive is now tried again when 64 MiB or less had arrived (a cut body was never retried; above 64 MiB it still is not); a TLS handshake the peer breaks with malformed or unexpected records (no shared protocol or cipher, or a captive portal answering plain HTTP on port 443) is no longer retried; the whole download and its retries share the 15 minutes; each attempt writes its own request: line, with retry= counting the attempts
* The runner no longer carries Zig's std HTTP client: the last users (the live feed, the action tarball downloads) run on the network library, so the std client's stale-TLS-clock workarounds (renew, keepFresh, preloadCa, the retired-client list), the std timing wrapper and the oracle tests that compared the two stacks are removed. The network library now reads the system CA bundle again when a handshake meets an unknown issuer (at most once a minute), which replaces what the std client's renew did for a CA added after the runner started
* The network library's test of where each phase of a request is timed no longer fails when the host's resolver is slow: it bounded the lookup of localhost at 50 ms, and a hosted runner took 600 ms. It still checks that the lookup is measured, that connect is the loopback's, and that neither the TLS nor the answer's delay is counted in them.
### Security
* A native job can no longer add entries to the jobs' bridge's MAC table with made-up source addresses, or move another job's address to its own port: each job's port drops frames whose Ethernet source is not its veth's MAC, learns nothing and floods no unknown unicast (#616)
* A native job's frames to a link-local group address (01:80:c2:00:00:0X) no longer reach the host's own sockets, IPv4 or IPv6, past the runner's rules: the bridge hands them to the host's stack as received on the job's own port, which the rules (they name zr0) did not cover; each port now drops them on ingress
