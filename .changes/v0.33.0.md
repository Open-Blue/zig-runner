## v0.33.0 - 2026-11-12
### Added
* Runner pools on one machine now share one memory budget: a root runner's gate counts the jobs the other pools started less than 2 minutes ago and have not yet used the memory of (recorded in /run/zig-runner/memory-budget), as it counts its own pool's, so two pools no longer admit a job each into the same free memory. A gate is stricter only while another pool has such a job. RUNNER_SHARED_MEMORY_BUDGET=false turns it off; a unit under ProtectSystem=strict needs RuntimeDirectory=zig-runner with RuntimeDirectoryPreserve=yes.
* A `health:` line in the runner's log once a minute while a job runs or waits (`RUNNER_HEALTH_INTERVAL`, 0 turns it off): memory, swap, pressure, load, what the memory gate has reserved, and each running job's name, age and memory, so that the last lines before an outage show what the machine looked like.
* RUNNER_NATIVE_DEFER_SYNC=false turns off the native store's deferred sync of a job's last layer (on by default); a pending layer is read only by the job that published it, and a layer whose deferred sync failed is refused at once, whoever holds it.
### Changed
* A native job's tool cache walk is cheaper when no file has to be read: the paths are joined and the digests' lines written without formatting, the entries are sorted by key, and a list whose every line was kept is not made again. The same two digests come out (a changed, added, removed or replaced file, link or directory is still caught), and the walk of Zig's 19,505 files takes 82 ms on the laptop instead of 118.
* Native jobs that open the tool cache together are all told the last job's walk of its trees, until the first process starts with it mounted, instead of all but one walking it themselves.
* The native backend makes a job's network namespace beside the job's image and caches instead of before them, and no longer asks the kernel to change a bridge that is already as wanted: with seven jobs starting together on a Raspberry Pi 5 the `netns` phase (33-130 ms each, 8 ms for one job) is off the job's critical path.
* A native step on a root runner now writes its upper through an idmapped mount where the kernel allows it, so its layer has the canonical ids on disk when the step ends and publishing it no longer walks and chowns every entry (a 20,000-file layer took about 570 ms to shift, a cold build's 64 ms on the Pi). Each step pays about 0.8 ms for the mount, and any machine or filesystem that cannot do it, and RUNNER_NATIVE_IDMAPPED_UPPER=false, keeps the shift as before; the layers and the store are the same either way.
* A job's last layer is renamed into the native store without waiting for its data to reach the disk, and is made durable in the job's teardown, after its result is reported (a pending mark naming the boot, refused in any other); the way a layer is synced (its own files or one syncfs) is chosen by the disk's I/O pressure and dirty data. A reported job may now lose its last layer to a power cut before its teardown sync: a clean cache miss.
* CI's End to end runs only its native pass on pull requests and in the merge queue: on GitHub's runner the Dagger engine was slow enough to fail jobs that were right, which took pull requests out of the queue while the native pass and main were green. The Dagger backend is still run end to end every night, and under ThreadSanitizer on every change to the runner's code.
* A native job that lost a step's layer to another job's pending one keeps caching its later steps over its own copy; a deferred layer whose sync fails mid-job warns in the next step's log; the store stress test also runs with the deferred sync.
* A native job on a root runner now writes a step's upper through an idmapped mount once it has made one large layer or is expected to (80 entries or more, by the size the step's layer had last time or its job's earlier layers), keeping the mount's user namespace in a file of the job's directory so later steps pay nothing to make it; with that, the idmapped upper is never slower than shifting the layer's ids afterwards.
* A native job's set-up spends less where jobs start together: it no longer asks the kernel for a link that is not there by name (which made it run `modprobe netdev-zrhN`: 5 ms a job in the `slot` phase, more in a burst), a dead job's veth of the slot is removed by the job's network helper, beside the rest of the set-up, instead of by the job itself waiting on the kernel's lock for link changes (20-30 ms with seven jobs starting together), the helper starts before the cgroup is made, and the image store's directories are not chmod-ed when they are already 0700. The slot's lock, the job's limits, rules and ids are as they were.
* The last job out's walk of the tool cache's trees runs on a thread after the job has let go, so a runner takes its next job without waiting for it; a job that opens the volume meanwhile waits for the walk and is told its verdict.
* CI's apt steps fall back to other Ubuntu mirrors when Ubuntu's own archive is unreachable: `.github/scripts/apt.sh` retries against kernel.org and Leaseweb (amd64) or Berkeley and Chemnitz (arm64), keeping apt's signature checks, and the provisioned image and end-to-end rootfs builds do the same when the archive does not answer.
* `RUNNER_NATIVE_DEFER_COLLECT=false` runs a native job's store upkeep before its end returns, as before (default true: on a thread after it); `native-phases.sh` reads the upkeep's own log line, which names the jobs it served.
* A native job's end no longer waits for the store's upkeep: the sync of the layers' directory and the eviction pass (`Store.collect`) run on a thread once the runner is polling again, one pass at a time, serving every job that ended meanwhile. On a Pi 5's SD card they took 12-24 ms of a job's end and 200-700 ms under load. A job's end still collects before it returns when the store may be past its cap by more than a sixteenth (at least 64 MiB, per runner process), when the disk is short of its floor, for the first job of a process, or after a failed sync; a stopping runner waits for the syncs without a limit and for the collect for five seconds.
* Make the analysis workflow lighter on pull requests: Valgrind runs only the changed tests, Fuzz 50K runs a target, Stress one job of 5 rounds, Store stress 90 seconds a pass, and Coverage runs only at night; both ThreadSanitizer jobs, native and end to end, run on every pull request that changes the runner's code; the nightly run is unchanged.
* Run CodeQL's go and python analyses only when Go or Python files change, and actions on every change; the weekly run analyzes all three, and CodeQL no longer runs in the merge queue, where it is not required and each pull request and push to main is analysed already.
* SPIN checks the store's locking liveness too, with the TLA+ module's own fairness; a new mutant shows the fairness forces no crash.
* SPIN checks the store's eviction and the release pipeline models too, with the same states as TLC; TLC no longer runs any of the three modules.
* SPIN checks the store's deferred-sync model too, with the same states as TLC.
* The analysis workflow no longer runs on draft pull requests: it runs once a pull request is marked ready, and on each push after, so drafts' pushes no longer take the hosted runners the merge queue waits for.
* CI takes fewer hosted runners: the branch name, ZLint and Go tools checks are steps of the Workflows job, not jobs of their own, and "Branch name" is no longer a required check.
* Test runs name their slowest tests (each past 2 s, up to five), and under ThreadSanitizer three single-threaded exhaustive tests are skipped, saying why: they found nothing for it and took 69, 51 and 35 s of a Database tests part; the Tests jobs still run them.
* CI's longest jobs are shorter: the store stress test runs for 10 s in ci (analysis still runs it for minutes on every store change and nightly), a run split into parts shares its slow tests out among the parts on their own, and the Workflows job runs apt.sh's mirror fallback test only when apt.sh or its test changes.
### Removed
* TLC and Java are gone from the tooling: SPIN checks every model, its state counts are the reference, and the TLA+ modules stay as documentation.
### Fixed
* The memory gate sizes jobs more carefully (from Autopilot, Borg and HTCondor): a learned size reserves RUNNER_MEM_MARGIN_PERCENT (10) more than was recorded, a learned size falls by at most an eighth a run after its heaviest run leaves the last five instead of in one step, a native job killed for memory is learned at half as much again (up to its memory.max and the machine's memory) instead of as the small run it was cut to, and for 30 s after such a kill no big job starts beside others unless nothing else runs. The memory-gate file is now v3; v2 files are still read.
* A native job's Docker action that starts while the job's limit is already near no longer loses its SIGINT: the helper holds the signal until the action's first process has a handler for it, as the kernel drops a signal to a namespace's PID 1 that has none, and the ThreadSanitizer job's test of each post script hearing its own SIGINT failed on it.
* A native job's layer store now fails closed when a sync fails: a failed fsync, write-back wait, syncfs or layers-directory sync fails that publish (nothing renamed in, the staged entry removed, the step's result unaffected), is logged once with its errno and never retried on the same descriptor, and the job publishes nothing more and evicts at its end every layer it renamed since its last successful sync, as an error already told to one descriptor could make a later sync report success for data that was lost.
* The nightly analysis passes again: the OCI layer fuzz test no longer fails on a race in the test's own thread pool, and Valgrind no longer reports the stack probe of a publish or fails on a signal test it cannot run.
* When CI falls back to another Ubuntu mirror while building a container (the provisioned image, the end-to-end rootfs), the container's apt sources are put back afterwards, so an image built during an outage of Ubuntu's archive ships the same sources as one built without it.
* The pgsink test of a quiet job's last lines waits up to 10 s for the background flusher's write instead of a fixed 600 ms, which a loaded stress run could outlast.
* The runner's console no longer races when two jobs log at once: its lock lives outside the log sink, which LogSink copies whole on every line, so no job reads it unlocked; the test of a job waiting for room in memory gives each waiting job its own log, as the runner does, where both shared one (ThreadSanitizer reported 19 races).
* The eviction test of names a job planted under a dead tree waits up to 120 s for the removal instead of 300 passes of 15 ms, which a loaded machine ran past: it needs about 170 passes alone and 256 under ThreadSanitizer.
* yamldiff stays on go.yaml.in/yaml/v3, the parser nektos/act reads workflows with, and drops a v4 requirement nothing imports; Renovate no longer proposes its major.
* The repository no longer holds a built yamldiff (4.9 MB) that #503 committed by mistake, and .gitignore keeps out what go build writes in each Go tool's directory.
* A native Docker action's PID 1 that sets its signal handler late, as a post step's sh under load does, still hears the step's SIGINT: the helper holds the signal until PID 1 has a handler for as long as the stop's stage lasts, where it gave up after 2 s and sent it to be dropped.
* A stopping runner whose store collect outlasts its 5 s wait ends at once, which the store survives as it does a crash, instead of tearing down the I/O the collector's thread still uses; the store's stress workers wait for their last jobs' upkeep before they end (ThreadSanitizer reported the race in both stress tests).
* The store stress test's run with the deferred sync is no shorter than 10 s (or all of the budget, when that is less): at ci's 10 s budget it ran 5 s, too few jobs to see a volume evicted, and failed its own check that one was.
