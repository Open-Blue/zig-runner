## v0.24.0 - 2026-11-02
### Added
* docs/native-backend.md: the plan for running steps in the runner itself, with namespaces, overlayfs and chroot, in place of the Dagger engine. A `Backend` boundary between job orchestration and step execution, `RUNNER_BACKEND=dagger|native` (default dagger) with a per-job fallback to Dagger for what native cannot do yet, nine phases with exit criteria and measurements, the result that would make us stop at the hybrid, and a running log of what each phase learns.
* A native step backend, behind `RUNNER_BACKEND=native` (the default stays `dagger`): a job whose steps are `run:` scripts and the built-in checkout, on the default image, runs its steps in the runner itself, through the same code for scripts, env, file commands, masks, live logs, conditions, timeouts and cancellation as on Dagger. On a root runner each job gets a range of host ids of its own (`RUNNER_NATIVE_SUBID_BASE`; its root and runner user are nobody on the host) and a network namespace of its own on the runner's bridge `zr0` with NAT (`RUNNER_NATIVE_SUBNET`, by default 10.211.0.0/16: its own `lo` and ports, no reach to the host's services or to other jobs); slots are locked host-wide under `/run/zig-runner`, which a systemd unit needs as `RuntimeDirectory=zig-runner` with `RuntimeDirectoryPreserve=yes`; each step gets a fresh overlay, mount, PID, UTS and IPC namespaces, `pivot_root`, runc's masked and read-only `/proc` (a mask that cannot be applied fails the step), Docker's default capabilities, a seccomp deny list (io_uring refused, `personality` limited to Docker's values), and `no_new_privs` (but for the runner user on a root runner, whose sudo reaches only the job's own root). It is not yet a boundary for untrusted jobs: no cgroup limits, and native runs only jobs the runner vouches for. A rootless runner sends jobs to Dagger unless `RUNNER_NATIVE_ROOTLESS=1`. Anything native cannot do yet (`container:`, `services:`, `uses:` actions, a custom image, `hashFiles()`, submodules) runs on Dagger, and "Set up job" says why. The rootfs is a provisioned `ubuntu:24.04` directory (`RUNNER_NATIVE_ROOTFS`) until the native image pull. On the laptop a trivial step takes 33 ms against about 224 ms on Dagger. docs/native-backend.md has what the runner needs and what this taught.
* Native steps get the step cache: a layer store (`native/Store.zig`) keeps each step's layer, output and file commands under the model's key (parent, script, stable env; P8's preimage format), so a job run again replays unchanged steps from the store instead of running them, its log the live one's byte for byte, its file commands applied again. Only a step that exited 0, uses no secret and follows a stored step is kept, so a failure is never replayed (#69) and no layer or log holds a secret; a commit's checkout is kept like a step. Layers are published by one rename that never replaces, one flock per key keeps two jobs sharing the store from running one key twice, a job holds the layers it uses so eviction (least recently used first, past `RUNNER_NATIVE_STORE_MAX_MB`, by default 10240) never takes them, a stack past 100 layers is flattened with hard links, and a layer's digest is deterministic (paths, modes, ids as the job sees them, xattrs, content). The store is mode 0700 (its layers hold files owned by the jobs' ids). Native stays off by default; the Dagger backend is unchanged.
* Native image pull (phase 3 of the native step backend, behind `RUNNER_BACKEND=native`): the runner pulls a job's image itself, a Zig port of the registry protocol with token auth and a `container:` job's `credentials:`, an index narrowed to linux/amd64 or arm64, gzip and zstd layers, whiteouts and opaque directories, blobs checked against their digests and kept content-addressed, and every layer unpacked inside the rootfs and nowhere else (no `..`, no symlink or hard link out, device nodes left out). The default image is provisioned by a native step on it, keyed by the image, the script and its env and kept in the store, so no Dagger session is needed to make the rootfs and `RUNNER_NATIVE_ROOTFS` is now optional. `container:` jobs and any image run natively (a job container's `ports:`, `volumes:` and `options:` still go to Dagger), with the image's env and `USER`, and "Set up job" says how the image and its provisioning were got. The Dagger backend is unchanged.
* Native steps (`RUNNER_BACKEND=native`) get cache volumes, a cgroup per job and the memory gate's per-job accounting. The package caches, the tool cache, Zig's package tarballs and local cache (with its generations), uv's environment and the minisign-verified Zig cache seed work as on Dagger: host directories under the native store bound into every step, never part of a step's layers, with the `repo` and `untrusted` scopes as separate trees and Dagger's sharing modes kept with flock (shared by default); on a root runner a volume's files are owned by a range of ids of its own, past the slots', and each job sees them as its own through an idmapped mount, nosuid and nodev. Each native job runs in a cgroup v2 of its own with `memory.max` (`RUNNER_NATIVE_MEMORY_MAX_MB`, by default three quarters of the machine's memory) and `pids.max` (`RUNNER_NATIVE_PIDS_MAX`, by default 8192), so a runaway job is OOM-killed in its own cgroup and a fork bomb stops at its own limit, and the step's log says when it hit either. The cgroups go under `/sys/fs/cgroup/zig-runner` on a root runner, or in a cgroup delegated to the runner (`RUNNER_NATIVE_CGROUP=self`, under `Delegate=yes` or `systemd-run --user --scope -p Delegate=yes`); without one a native job runs as before, and "Set up job" says why. The memory gate measures a native job in its own cgroup instead of the Dagger engine's, so two overlapping jobs are no longer charged for each other: holding 300 MB each, the first measured 304 MB against 610 MB engine-wide.
* Native `services:`, behind `RUNNER_BACKEND=native` on a root runner: each service runs as a long-running sandbox of the runner's own (its own mount, PID, UTS and IPC namespaces, the job's ids, Docker's capabilities and seccomp filter, a fresh overlay over its image) in the job's network namespace, which the steps share; steps reach it by name and on `localhost` at each published port (a TCP relay of the runner's own when the numbers differ). A service is ready when its health check passes (`--health-cmd` and the other `--health-*` options, or the image's `HEALTHCHECK`), run inside the service, or else when its ports accept connections, as on the Dagger path; "Stop containers" stops it and prints its logs. Images come from the native image pull, with the service's credentials; a job whose service image is given by an expression runs on Dagger. Each service and its port relay run in the job's cgroup. The jobs' NAT rules now also drop what goes to `zr0` and is not a reply, so neither the host nor anything it routes reaches a job's services. docs/native-backend.md has the measurements and what this taught.
* Native steps run `uses: docker://<image>` steps (behind `RUNNER_BACKEND=native`): the action runs in its image's filesystem in a sandbox of its own, with the job's workspace and its home, workflow and file-command directories bound in at the paths GitHub binds them, its entrypoint, args, env, inputs and file commands as on Dagger, and what it writes in the workspace in the job's next layer without a copy (given to the runner user, as Dagger gives it). Its image comes from the native image pull; a step whose image runs as a non-root `USER` sends its job to Dagger, as `uses:` Docker actions still do. On the laptop a `docker://` step takes about 11 ms natively.
* The Lean proofs cover the native step store (P8 of docs/native-backend.md): `Runner.Native` proves that the native key as P2's store hashes it (the parent's key, the script, the stable environment, then the user, working directory and kept files, every field length-prefixed, and for a base the digest of the rootfs, id mapping, slot and binds below it) keeps exactly what the model's key keeps (mounts, volatile variables and the event payload stay out); that a job run against a store other runners share, which records only successes of unmarked steps, produces what it does with the step cache off, under the same hypothesis as on Dagger and whatever other runners publish or evict and whichever reads fail; that which of two racing writers wins does not matter; that an entry must be read whole or be a miss; and what a layer digest must hash (a sorted walk, nothing that differs between runs) for output keys. P2's layer walk now counts each entry's xattrs, without which two different layers could share a digest. `keyoracle` writes the key and layer vectors runner/src/native/key_vectors.zig checks the Zig key against, until P2's own hashing takes its place there.
* A native Dockerfile interpreter for Docker actions, not yet wired to jobs (they need the native action loader first): it parses a Dockerfile as Docker does and builds `FROM`, `RUN`, `COPY`, `ADD`, `ENV`, `WORKDIR`, `ENTRYPOINT`, `CMD`, `ARG`, `USER` and `LABEL` as a chain of keyed layers (each key from its parent's, the instruction as evaluated, and what it reads: the build arguments for `RUN`, the sources' content for `COPY`), taken from a layer store when the key is there. Multi-stage builds, wildcards, `ADD` of URLs or archives, `SHELL`, `ONBUILD` and heredocs are refused with the line and the reason.
* An end-to-end check before merge ("End to end" in ci, `.github/scripts/e2e.sh`): the runner built from the pull request serves real workflows on GitHub's runner, through GitHub's broker and the pinned Dagger engine, once on Dagger and once with `RUNNER_BACKEND=native`. It registers just-in-time runners on Open-Blue/runner-bench under a label of the run's own (as the GitHub App `zig-runner-e2e`, whose key only the `e2e` environment holds, so fork pull requests skip it, still reporting), dispatches runner-bench's `e2e.yml` and `e2e-cancel.yml`, and checks jobs, steps and logs through the API: a script installing into the tool cache (what v0.22.0 broke), a service, a `docker://` step, a JavaScript action, the file commands, a masked secret, a cancelled run, and a rerun replayed from the step cache. Each job's times on both backends go to the `e2e-timings` artifact. `e2e.sh check <label>` runs the same suite by hand against a running pool, in place of the manual smoke test before a release. `zig-runner --provision-script` prints the script that provisions the default image, for making the native backend's rootfs. Not a required check yet.
* Native steps run `uses:` actions (behind `RUNNER_BACKEND=native`): every remote action is fetched by git in the job's image before "Set up job" and read from there, Docker actions run natively (with a `docker://` image from the native image store, or built from their Dockerfile into keyed layers kept under the native store and reused across jobs), and composite actions run their steps natively. A job with a JavaScript action or a local action (`uses: ./...`) still runs on Dagger, and "Set up job" says why.
* Native steps run JavaScript actions (node20, node24) with pre, main, post and `post-if`, through the same code as on Dagger, with the runtime pulled natively (its musl build in a musl image) and bound nosuid and nodev; and local actions (`uses: ./...`), judged before the job from the job's own repository at its commit and read from the workspace when they run. A local action built from a Dockerfile, or one not in the repository at the job's commit, still sends its job to Dagger.
* Native steps (`RUNNER_BACKEND=native`) share stored layers across slots on a root runner: a layer is published with the canonical ids (the ids the job's namespace saw, 0 to 65535; any other host id becomes the overflow id; set-id bits, file capabilities and ACLs kept), and each step mounts the stored layers idmapped onto its own job's range, read-only, nosuid and nodev, as it already did the rootfs and the Zig cache seeds. The slot left the step store's key (the store's format is now 3, so older layers age out), so a rerun replays whichever slot it lands in, where before it mostly missed in a busy pool. Root and rootless runners keep separate keys; rootless runners are unchanged. Native stays off by default; the Dagger backend is unchanged.
* The Lean proofs' CI (proofs.yml) has three gates where it had one plain `lake build`: `lake build --wfail`, so a `sorry` (a warning until now) or any other warning fails the check; `lake env leanchecker`, which replays every declaration of the `Runner` and `Glob` libraries and the oracles in the kernel from the built `.olean` files; and `proofs/Axioms.lean`, which fails when any declaration in `Runner` or `Glob` depends on an axiom outside its allow list (`propext` and `Quot.sound`, what the proofs use today: no `Classical.choice`, `sorryAx` or `Lean.ofReduceBool`), when a module there declares an axiom, or when one of the 61 main theorems it names is missing, and prints `#print axioms` for each of them. No theorem changed; proofs/README.md documents the gates. The runner itself is unchanged.
* The comparison tools' Go (the six modules under `runner/tools`, the test oracles the weekly `compare` runs) is linted with `go vet` and staticcheck 2026.2.2 (`.github/scripts/go-lint.sh`, which builds staticcheck at its pinned version with the newest toolchain the modules name, kept current by Renovate): by "Go tools" in `ci` on a pull request that changes them or the script (skipped, still reporting, otherwise, by `ci-scope.sh go`), and weekly in `compare`, which also runs govulncheck for information. They had no findings. The runner itself is unchanged.
### Fixed
* The native step store, after review: a rootfs provisioned again in place is noticed (the rootfs's fingerprint now covers ctimes and inodes, and every job checks the root and a `.zig-runner-provisioned` stamp the recipe touches); the store's format is in every key, so layers do not outlive a runner upgrade that changes their meaning; a vouched fork's pull request keys its layers apart from its repository's jobs (the package caches' scope); a record that cannot be replayed is refused at publish, and a stored entry is checked whole on every hit (lengths and sha256s in a `meta`) and evicted when it is not; entries are synced to disk before the rename that publishes them; a lock is not leaked on an error, and an upper that cannot be put back is never deleted; a layer's size is counted with no depth limit and a layer that cannot be counted whole is not published.
* Native steps get the tool cache, as Dagger steps do (#261): each job's base makes `/opt/hostedtoolcache` (`RUNNER_TOOL_CACHE`) owned by the step user, so a script that installs into it, such as zig-runner's `install-zig.sh`, no longer fails natively with `mkdir: cannot create directory '/opt/hostedtoolcache': Permission denied`. What a step puts there is in its layer and comes back with its replay, until phase 4's cache volume takes the directory's place. Native stays off by default; the Dagger backend is unchanged.
* CI's runs are free of annotations that were not about them: the tests' output is only text to the job that runs them (`::stop-commands::` in `zig-test.sh` and in ci.yml's `zig build test`), so the native backend's runaway and fork-bomb tests no longer raise "The job reached its process limit" and "its memory limit" as CI's own errors; and the GitHub-hosted jobs are pinned to `ubuntu-26.04`, not `ubuntu-latest`, ending the migration notice on every job and making an image upgrade, which moves what the native passes stand on, a deliberate change. The runner itself is unchanged.
* Running out of memory is reported as that, never read as an answer: a broker message is no longer ignored as one of type `''` (a job request dropped), `if: always()` after a failed step no longer skips the step, a valid `fromJSON()` argument is no longer "invalid JSON", a regular expression's `(?(...)...)` is no longer refused, a numeric `github.run_id` is no longer left empty, and an image's manifest, index or config is no longer "not one" (nor a just-unpacked image "lost by the store"). Found by new allocation-failure tests (`runner/src/alloc_failures.zig`, `std.testing.checkAllAllocationFailures` and a one-failure-at-a-time variant) over YAML, expressions, regular expressions, HPACK, hashFiles, the job and broker messages, OCI references, manifests and configs, tar and PAX headers and a whole layer. The `@bitCast` uses were audited against Zig 0.17's new definition (one, an address array cast to an integer, now reads the bytes directly), and CI counts the casts and assertions that skip Zig's checks against a checked-in baseline (`.github/scripts/unsafe-ratchet.sh`).
* A change file with an unescaped apostrophe in its single-quoted body (native services, Added-20261101-120600) stopped v0.24.0 at its Tag step; it is fixed, and the Workflows job now batches every unreleased entry as a dry run, so a change file that is not valid YAML fails the pull request that adds it.
### Security
* Native steps (`RUNNER_BACKEND=native`): the seccomp filter is now Docker's default profile as an allow list, for x86_64 and aarch64 (a call it does not name gets EPERM, one newer than it ENOSYS; `clone` without namespace flags, `personality` and `socket` limited to Docker's values), instead of a deny list. The jobs' NAT and firewall rules are made over nftables netlink instead of with `iptables`, in a table of the runner's own (`ip zig_runner`) that forwards the jobs' traffic only out through the host's uplinks, plus `-i zr0`/`-o zr0` accepts in the host's iptables-nft `FORWARD` and `DOCKER-USER` chains; P1's iptables rules are replaced. No `iptables` binary is needed. Jobs the runner does not vouch for still run on Dagger until each native job has cgroup limits (phase 4).
* CodeQL runs from a checked-in workflow (`.github/workflows/codeql.yml`) in place of the repository's default setup: the workflows (actions), the comparison tools under `runner/tools` (Go, built by autobuild) and the Unicode table generator (Python), each a job of its own on the pinned `ubuntu-26.04` (ending default setup's `ubuntu-latest` migration notice), with the `security-extended` queries instead of the default suite, on every pull request, in the merge queue (so it can become a required check), on every push to main and weekly. Its uploads are refused until default setup is turned off. The runner itself is unchanged.
