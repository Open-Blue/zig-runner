## v0.36.0 - 2026-11-19
### Added
* RUNNER_CARGO_TARGET_CACHE=true (with RUNNER_ZIG_LOCAL_CACHE) keeps cargo's target directory between jobs, in Zig's local cache volume (cargo-target/), so a Rust library a Zig build compiles, such as zig-runner's own zr-net, is not compiled again by every job: same scope (repo jobs only; an untrusted job's is its own), same size limit and generations, on the Dagger and native backends; a job keeps the generation it started in even when another job rolls the cache. Repo-scope jobs that run Zig now get the scope's cargo registry volume too (untrusted ones do not), and build-zr-net.sh uses it, builds offline (--frozen) first and falls back to the network, so a failing crates.io lookup no longer fails a build whose crates are cached. See docs/OPERATIONS.md, Cargo's caches.
* On a push to main, the Pi's tests are compiled on GitHub's fast runner and only run on the Pi: a "Tests, compiled for the Pi" job cross-compiles the tests, the runner and the shard runner for aarch64 musl (LLVM, debug info kept), and "Tests (x86_64)" downloads that one tar, checks it against the sha256 the build job output, and runs it (.github/scripts/zig-test-prebuilt.sh), so the Pi no longer spends its two minutes and 4 GB of memory compiling. Pull requests compile in the Test job as before (docs/CI.md).
* Native jobs can have a Docker-compatible API of their own (#448, stage 1a): RUNNER_NATIVE_DOCKER_API=true (off by default; nothing changes while it is off) serves a unix socket per job, bound into every step at /var/run/docker.sock with DOCKER_HOST and DOCKER_BUILDKIT=0 set (a workflow's env: wins), torn down with the job and never the host's. It answers /_ping, /version and /info for the CLI; every other endpoint, builds included until stage 1b, gets HTTP 501 'not supported by zig-runner yet: <METHOD> <path>', and BuildKit's endpoints a hint. Requests are bounded and time out; a job that used the API logs one kind=native_docker_api line. See docs/OPERATIONS.md and docs/native-backend.md.
### Fixed
* A deploy's restart no longer kills the native jobs a runner is running: deploy/zig-runner.service sets KillMode=mixed, so systemd's SIGTERM goes to the runner alone, which lets running jobs finish (RUNNER_STOP_GRACE_SECS) as it says. With the default, control-group, the signal also reached every process of the jobs in the unit's cgroup and their steps died at once (exit 143). Existing units take it with a drop-in (docs/OPERATIONS.md).
* spin.sh (the SPIN model checks of the pre-push hook and CI) sizes its parallelism to what it is given instead of one check a core: the cores are nproc and the cgroup's cpu.max quota, and a configuration starts only while the estimates of the running pans (hash table plus states, measured per configuration) stay within 70% of the memory left under the cgroup's memory.max or memory.high and MemAvailable, so a push in a 4 GB scope no longer ends in an OOM kill. SPIN_JOBS=N overrides it. The configurations and verdicts are unchanged.
* The unit tests run faster, and the two long eviction tests no longer fail on a loaded machine: they wait for the count of passes eviction guarantees, not for a 120-second deadline, and run with a clock that stands still. ZIG_TEST_TIMES=1 prints every test's wall time and each shard's busy time. The allocation-failure sweeps fail a sample of the allocations (the first and last, each call site's first visits, then every power of two, at most 48 runs of a sweep), the bit-flip fuzz tests flip the header, the end and every 7th bit of each seed, and the hashFiles many-entries test and the eviction chains use smaller trees; ZIG_TEST_FULL=1 runs everything as before. See CONTRIBUTING.md.
* The network library's test of a call that runs too long no longer fails on a loaded CI runner: its whole-call deadline is 2 s instead of 300 ms, which the response head also had to arrive within (it failed with status 0 in main's Database tests job on a GitHub-hosted runner).
* CI on a push to main: "Every test file is compiled" runs in the hosted prebuild job, not on the Pi (about 2.5 min and 3.6 GB less on the Pi job, to be confirmed on the first push to main), and the Test step's `memory-peak:` line reports a peak on the prebuilt path (sampled from /proc where there is no cgroup or GNU time) instead of "unavailable".
* e2e.sh says why it could not find a dispatched run: the suite's time ran out, the last GitHub API error (a rate limit or an outage used to read the same as a run never made), or no run of that title among the 50 newest dispatches. PR #586's ThreadSanitizer end-to-end job failed once with only "the e2e run never appeared" and passed on a rerun.
* The Dockerfile oracle's bases.txt pins alpine 3.24, as its fixtures do since Renovate moved them (#580); it still named 3.22, so the oracle looked for a base it had not prepared. Renovate's rule for bases.txt never matched (its ^...$ anchors apply to the whole file, which holds two lines) and is fixed.
