## v0.37.0 - 2026-11-20
### Added
* Job priority (#549): a job paused by RUNNER_PRIORITY_FREEZE keeps its timeouts: the time it was paused (monotonic, all pauses added) moves the deadline of the running step and, where the runner enforces it (Gitea and Forgejo), of the job, so a pause never eats a timeout-minutes. The step-end line carries paused_ms= for a paused step, "Set up job" says a pool may pause, "Complete job" says how long the job was. Not extended: a GitHub job's own timeout-minutes (GitHub enforces it), the readiness waits of services and image pulls (set-up, before the steps run). docs/OPERATIONS.md documents job priority and that the policy file format is experimental until it has run on real pools.
* CI jobs say what the runner image gives them (image, kernel, page size, cgroup version, each tool's path and version) as their first step, and fail naming every missing tool (nft, ip, unshare, python3, Docker), instead of a test that blames itself
### Fixed
* CI: ThreadSanitizer's native job gives the store stress test 60 s, so its eviction check no longer fails on a slow run.
* A job reaches a Gitea or Forgejo that is a Docker container with a port published on the host's own address (-p 10.0.0.5:3000:3000, with that address as ROOT_URL): the jobs' forward rule matches the connection's original destination (ct original ip daddr and proto-dst), not the address Docker's NAT has already rewritten, so the job's connections no longer time out. The rule takes the connection's first direction only and not a packet going back out of the jobs' bridge, so a packet made up to look like a reply to another job's connection is no longer forwarded back to the bridge by it; packets with no connection (invalid, untracked) match nothing and are dropped in forward. A job reaches what the published port maps to, by that address and port, and no other published port or container address (root tests on the wire, with a second job making up replies). What it does not change: jobs on the shared bridge can still send packets with another job's source address in the first direction (#603), and a local REDIRECT or a DNAT to a port of the host itself is matched in input as before, by the address and port as dialled.
* The release's aarch64 binary links again on runners without Rust 1.99.1 (GitHub's ubuntu26 image of 2026-11-16 on): install-rust.sh, sourced by build-zr-net.sh, set its own arch to the machine's and so replaced the build's, which then built the network library for x86_64 again and copied it under the aarch64 name (the link failed on every object, "incompatible with aarch64linux"). The installers' variables are now rust_-prefixed, build-zr-net.sh makes what it was asked for read-only (a sourced script that assigns it fails at once, by name) and checks the archive's ELF machine before handing it on. The job's log now says, for each build, the architecture asked for, cargo's target, which cargo from where, whether Rust was reused or unpacked, and the archive's architecture, member count and SHA-256.
* The nightly analysis: the fuzz job says its corpus, runs and time; the memory soak waits for its container's packages with retries and says what it did when the runner does not start; Install Zig no longer prints sha256sum's FAILED line when it downloads
* The runner builds again on a machine with libunwind's development package installed (Ubuntu's libunwind-dev): the build asked pkg-config for libunwind, which added the host's glibc include directory (-I/usr/include/x86_64-linux-gnu) to a musl build, and the vendored zstd and zlib-ng failed to compile with 37 errors. The build now links Zig's own libunwind without asking pkg-config.
* A runner with a GitHub App no longer exits at its start when its first token request fails on the network: a failed name lookup, a refused or reset connection, or GitHub answering 5xx or 429 is tried again after 1, 2, 4, 8 and 16 s (one github_app_retry warning each), and a stop signal ends the wait. Only a refusal (4xx) still gives the hint about the App's installation; a network failure that outlasts the retries says to check DNS and the network instead. Before, one DNS miss on a GitHub-hosted VM stopped the e2e suite's runner, its jobs stayed queued and the hint blamed the App. The e2e suite now fails as soon as the runner it started has exited, with the last of its log, instead of waiting out each run's timeout.
* CI's apt.sh says what it probed and chose, on stderr in the job's log: each archive and mirror URL with its HTTP status and time, or curl's error, and whether the configured sources or which mirror were used. apt.sh probe ARCH CODENAME prints one such line. The e2e suite's native rootfs build logs its image and container, and while it is waited for, a status line every minute: the container's state, how much apt has fetched, its running apt and dpkg processes, and how Ubuntu's archive answers now; a timeout says the last status. A slow archive is then told apart from a hung build.
* CI: one Scope job decides every scope once, and the jobs it rules out are skipped before they take a hosted runner, so a documentation-only change no longer queues for about eleven runners
* The merge queue's ci run reuses a pull request's pass when it tests the very same tree on the very same base, and skips the heavy jobs instead of running them again
* The test of a step paused past its timeout no longer fails on a busy runner: it held the step's paused time to the nominal 1.2 s, but the pause it ends runs 1.2 s plus however late its sleep wakes, so a slow arm64 runner measured more (Tests (arm64), 2026-11-20). The bound is now the pause as it was recorded.
* ThreadSanitizer no longer reports a false data race in the Dagger session's log reader: the process heap wrapper declines to remap in a sanitized build, because ThreadSanitizer does not intercept mremap.
* The ThreadSanitizer end-to-end stop prints why a runner that ignores SIGTERM did not stop (process tree, thread states, signal masks, log end) before killing it (#628)
* The nightly ThreadSanitizer end-to-end check ignores a job GitHub lists twice (one that never had a runner) and, when jobs report no step for five minutes, prints the runner's threads, the engine's log and each run's jobs before cancelling
### Security
* A native job on a root runner can no longer send packets as another job: each job's port on the jobs' bridge has a table of its own in the nftables bridge family (zig_runner_pin<slot>) that drops IPv4 whose source is not the job's address, and ARP whose sender is not, before anything is routed or forwarded (#603). The job's network helper makes it before the port exists and in the host's namespace, and fails the job's network if it cannot (a kernel without nf_tables_bridge); the job's teardown removes it, and a crash's leftover is replaced by the slot's next job. Root tests on the wire send spoofed TCP and ARP as another job's address, with and without the pin, and check a real job's pin is on the host while it runs and gone after.
